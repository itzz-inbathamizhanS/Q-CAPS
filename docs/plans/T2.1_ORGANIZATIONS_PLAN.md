# T2.1 Organizations, membership and roles: plan

Status: **implemented (minimal scope)**, 2026-10-05. Written as a PLAN FIRST task; the owner asked for all tasks to
proceed without stopping for review, so it was implemented straight after. Code: `backend/main_api/organizations/`
(`access.py` for every permission decision, `routes.py`, `cli.py`); tests: `backend/tests/test_organizations.py`
(the section 7 matrix). Not yet built: the researcher aggregate endpoints (T3.1/T2.4) and an organization UI beyond
the asset labels (T2.4).

Scope, following the single-paper decision in the implementation plan, §4:

- **Organizations:** one organization type plus a clearly labelled **lab** organization for the study.
- **Roles:** `org_admin`, `member` and `researcher`. `instructor` is defined but grants nothing extra yet.
- **Out of scope:** multi-tenant billing, invitations by e-mail and SSO.

## 1. Model

| Table | Columns | Notes |
|---|---|---|
| `organizations` | `id`, `slug` (unique), `name`, `kind` (`organization` or `lab`), `created_by` (FK users), `created_at` | Lab organizations are shown as "Lab environment" everywhere. |
| `organization_memberships` | `id`, `organization_id` (FK), `user_id` (FK), `org_role` (`org_admin`, `member`, `instructor` or `researcher`), `created_by`, `created_at` | Unique on (`organization_id`, `user_id`). One role per person per organization. |
| `assets.organization_id` | exists today, unused | Becomes the owning organization. Personal assets keep it NULL. No foreign key can be added to an existing SQLite column, so the code enforces it. |
| `interventions.assigned_user_id` | new, nullable | The learner responsible for an intervention on an organization asset. For personal assets the owner is the learner, as today. |
| `audit_events` | `id`, `at`, `actor_user_id`, `organization_id`, `action`, `target_type`, `target_id`, `details` (JSON) | Append-only. Records membership and role changes, asset context edits, intervention creation, verifications, exports. |

`users.role` stays `learner` or `admin` and means **platform** administration only. Roles inside an organization
come only from memberships, which the server reads; the client never supplies them.

## 2. Who can do what

`access.py` decides every permission. It provides `can_view_asset`, `can_manage_asset`, `visible_asset_filter(user)`
and `org_role(user, org_id)`, so that no endpoint keeps its own rule.

| Asset kind | View (findings, evidence, requirements, interventions, closures) | Manage (verify, asset context, assign interventions) |
|---|---|---|
| Personal (`owner_user_id` set, organization NULL) | owner, platform admin | owner, platform admin |
| Organization (`organization_id` set) | `org_admin`, `member` and `instructor` of that organization; platform admin | `org_admin` of that organization; platform admin |
| Legacy shared (both NULL) | everyone signed in (as today) | platform admin |

Researchers never see individual assets, findings or learners. They receive only aggregate endpoints (§5). A
researcher who is also a member through another membership sees what that membership allows; roles do not combine
within one organization.

## 4. Migration

- **New tables:** created by `create_all`. The two new columns are added with idempotent `ALTER TABLE`, following
  the existing pattern.
- **Existing assets:** all stay personal (`organization_id` NULL) or legacy shared. Nothing moves into an
  organization automatically; an `org_admin` re-scans a verified domain on behalf of the organization.
- **Command line:** `python -m organizations.cli create-org`, `add-member` and `create-lab` (platform admin, local)
  bootstrap the first organization. All actions are audited.

## 5. Researchers

- **Endpoints:** researcher endpoints live under `/api/research/...` and return counts and summary statistics
  only, never names, user ids, domains or finding ids.
- **Small groups:** any figure computed over fewer than **k = 5** people is withheld and shown as "insufficient
  data".
- **Export:** the anonymized CSV export (T3.1) uses per-study pseudonyms (HMAC of the user id with a per-study
  secret).

## 6. Lab organization (study)

- **Creation:** a platform admin creates a `kind = lab` organization.
- **Assets:** the T5.1 testbed endpoints. Their findings come from real scans of the testbed, imported with a
  command that only accepts results produced by the evaluation harness, never typed-in findings.
- **Membership:** study participants join as `member`.
- **Display:** the UI labels it "Lab environment", so nobody mistakes lab findings for their own infrastructure.

## 7. Authorization test matrix

Every combination of the following is tested:

- **Actors:** platform admin, `org_admin`, `member`, `researcher` (same organization), a member of *another*
  organization, a non-member, the owner of a personal asset.
- **Resources:** personal asset, organization asset, legacy shared asset; the finding, evidence, requirements,
  interventions and closures of each; the membership list.
- **Actions:** read, create intervention, verify, change membership.

Each cell expects 200/201, 403 or 404. The rule for 404 versus 403: a resource the actor may not even know about
gives 404, the same answer as for a missing id. A resource the actor can see but not change gives 403.

## 8. Limitations

- **Rate limiting:** limits stay in memory per process, which is correct only for one instance. A shared store
  (database or Redis) is needed before running more than one instance; that is recorded, not built here.
- **Instructor role:** defined but grants nothing beyond `member` until course-authoring permissions are designed.
